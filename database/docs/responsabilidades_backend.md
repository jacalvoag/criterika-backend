# Responsabilidades del backend y del entorno

La base protege relaciones, unicidad, rangos, históricos y determinadas condiciones transaccionales. El cumplimiento funcional requiere que el backend coordine las operaciones completas.

| Tema | Responsabilidad pendiente de implementación |
| --- | --- |
| Autorización | Validar sesión, identidad, estado, rol y titularidad en cada servicio. El backend usa un grupo técnico compartido; no hay RLS ni credenciales SQL por jugador. Sus permisos SELECT no aíslan titulares. |
| Contexto de auditoría | Iniciar una transacción, llamar a `criterika.establecer_contexto(tipo, actor, request_id, motivo)` con datos derivados del servidor y realizar la modificación en esa misma conexión. Nunca aceptar el actor indicado libremente por el cliente. El contexto SQL no valida JWT ni protege frente a un backend comprometido. |
| Auditoría | Los triggers capturan acciones administrativas de negocio y sus sujetos, fecha/hora, recurso, correlación y campos modificados. Solo una lista reducida de valores operativos se copia; los valores privados se omiten. Si falla la escritura del evento, se revierte la modificación. Las tablas técnicas de secretos no copian tokens ni hashes a la bitácora. |
| Intentos y evaluación | Validar elegibilidad, progresión, revisión publicada, contenido y criterios JSON con los schemas; evaluar respuestas y cerrar ejecuciones/actividad/intento coordinadamente. Una fila marcada APROBADO no constituye por sí sola prueba de una evaluación correcta. |
| Publicación | Comprobar el conjunto completo de unidad, nivel final y carta con sus tres etapas. Crear la revisión y sus componentes en una transacción. La base comprueba 3–6 actividades y un máximo de dos de cada tipo. |
| Economía | Bloquear el estado del jugador con `SELECT ... FOR UPDATE`, recalcular regeneración y reserva, comprobar saldo/capacidad y confirmar beneficio, movimiento, estado e idempotencia juntos. Los triggers comprueban correspondencia de origen e importe; no ejecutan la compra ni recalculan automáticamente el saldo o la racha. |
| Credenciales y PII | Generar hashes de contraseñas y tokens, validar expiraciones, limitar intentos y configurar logs por lista permitida. No registrar contraseñas, tokens, RFC ni datos bancarios. El SQL no configura los loggers de NestJS. |
| Aceptaciones | Registrar documento/versiones realmente mostrados, instante del servidor e IP obtenida de la conexión y de proxies confiables. La versión referenciada permanece estable. No confiar en una fecha/IP arbitraria enviada por el cliente. |
| Exportación | Construir JSON con datos del propio titular, incluidos los recursos indirectos relevantes. Excluir secretos y datos de terceros. Gestionar autorización, archivos exportados y caducidad de descarga. |
| Supresión | Coordinar restricción inicial, verificación de identidad, eliminación o anonimización operativa, objetos y terceros; depurar enlaces y referencias personales de auditoría. Las tablas de pasos permiten seguimiento, pero no ejecutan una purga por sí mismas. No marcar completado mientras existan pasos requeridos pendientes. |
| Respaldos y restauración | Conservar el control mínimo de eliminación hasta 60 días y mantener una copia protegida fuera del snapshot que pueda restaurarse. Reconciliar y reaplicar eliminaciones antes de habilitar una restauración. Respaldo máximo de referencia: 30 días, acortándolo cuando el plazo efectivo lo requiera. La tabla en el mismo respaldo, por sí sola, no evita reintroducir datos. |
| Retención y tareas | Implementar el trabajador/cron, plazos y reintentos idempotentes. La auditoría usa un vencimiento inicial de 179 días para dejar margen bajo el límite de 180 días; debe eliminarse oportunamente y depurar PII antes cuando proceda. Los plazos son decisiones operativas del proyecto que deben concordar con los documentos aprobados; el SQL no acredita cumplimiento legal. |
| Mantenimiento | Usar credencial separada. El modo transaccional `criterika.purga=true` solo funciona con rol técnico autorizado y evita recrear PII al depurar. El coordinador debe registrar la evidencia agregada de cierre y el control mínimo externo sin copiar datos personales borrados. |
| Cifrado y terceros | Configurar HTTPS/TLS con validación de certificado, cifrado en reposo y respaldos, gestión de claves y proveedores autorizados. Revisar qué datos recibe cada tercero y sus mecanismos de eliminación. Estos controles no quedan implementados al ejecutar DDL. |

Las pruebas de concurrencia incluidas ejercitan transacciones SQL de ejemplo con bloqueo de fila. Ese mismo patrón debe quedar integrado y probado en los servicios reales. Los endpoints y los trabajos de privacidad necesitan pruebas propias al implementarse.
